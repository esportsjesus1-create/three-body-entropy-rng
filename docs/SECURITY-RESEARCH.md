# Three-Body RNG Security Research Document

## Executive Summary

This document provides comprehensive security research for the Three-Body RNG provably fair gambling system. It covers known attack vectors, threat modeling, cryptographic guarantees, and implementation recommendations for a real-money transactional system.

**Critical Finding**: "Provably fair" is often misunderstood. It provides **post-commit immutability** (server can't change outcome after commitment) but does NOT automatically guarantee **unbiasability** (server can't choose favorable outcomes) or **auditability** (server can't selectively abort or hide losing rounds).

---

## 1. Known Attack Vectors in Provably Fair Systems

### 1.1 Server Seed Grinding (CRITICAL)

**Description**: If the server generates fresh server seeds per spin and can compute outcomes before committing, it can try many seeds and only commit to house-favorable results.

**Real-World Example**: This is the most common "operator degree of freedom" attack. The server:
1. Generates candidate server seed
2. Computes what outcome would result
3. If unfavorable, generates new seed
4. Only commits to favorable seed

**Impact**: Permanently alters house edge while still "verifying" correctly.

**Mitigation**: 
- Pre-committed long-lived server seed (seed chain)
- External randomness beacon (drand, blockchain)
- Two-party commit protocol

### 1.2 Shuffle-Based Attacks (BitZino Exploit)

**Description**: Casinos can pre-compute "optimized" initial arrangements that perform better against all possible PRNG seeds.

**Technical Details** (from BitZino research):
- Initial deck/arrangement is NOT covered by commitment
- Casino finds arrangements that beat theoretical expectation across all seeds
- Results still "verify" because the seed hash matches

**Impact**: House edge manipulation undetectable by standard verification.

**Mitigation**: Commit to ALL parameters affecting outcome (reel strips, mapping rules, initial state).

### 1.3 Selective Abort / Withholding Reveal

**Description**: Server commits honestly but refuses to reveal if outcome is unfavorable.

**Attack Pattern**:
1. Server commits to seed
2. Player bets
3. Server computes outcome
4. If player wins big: timeout, error, "network issue"
5. No reveal = no proof of manipulation

**Impact**: Server can selectively void winning bets.

**Mitigation**:
- Mandatory reveal within fixed time window
- Automatic refund + public logging of aborts
- Transparency log records all orphaned commitments

### 1.4 Uncommitted Degrees of Freedom

**Description**: Any parameter affecting outcome that isn't bound by commitment becomes an operator lever.

**Examples**:
- Game rules version
- Reel strip configuration
- Symbol mapping algorithm
- Physics simulation parameters
- Floating-point rounding mode
- Byte slicing / cursor position

**Impact**: Operator can change rules while passing "seed hash matches" check.

**Mitigation**: Commit to complete game state including all parameters.

### 1.5 Code Injection / Verification Tampering

**Description**: If operator serves the JavaScript verifier, they can selectively show "Verified" while running different logic.

**Attack Pattern**:
- Serve modified verification code to specific users
- Show "Verified" regardless of actual computation
- User trusts green checkmark without independent verification

**Impact**: Complete bypass of provably fair guarantees.

**Mitigation**:
- Reproducible builds with pinned hashes
- Subresource Integrity (SRI) for verification scripts
- Offline/independent verifier tools
- Open source verification code

### 1.6 Timing Attacks

**Description**: Server delays commitment until after seeing player input, or manipulates timestamp ordering.

**Problem**: Browser-local timestamps (T1 < T2 < T3 < T4) prove only local UI ordering, NOT that server didn't generate commitment late.

**Impact**: Server can compute outcome after seeing bet, then backdate commitment.

**Mitigation**:
- Transparency log with append-only guarantees
- Third-party timestamp authority (RFC 3161 TSA)
- Blockchain anchoring
- Commitment must appear in public log BEFORE client accepts spin

### 1.7 Client Seed Weakness

**Description**: Default client seeds generated by platform (not truly player-controlled).

**Attack Pattern**:
- Server provides "random" client seed
- Server actually knows the seed
- Server can compute all outcomes in advance

**Impact**: Eliminates player's contribution to randomness.

**Mitigation**:
- Generate client seed in browser using WebCrypto
- Allow player to override/provide own seed
- Never let server supply default without user visibility
- Consider commit-to-client-seed flow

### 1.8 Nonce Manipulation

**Description**: Server controls nonce sequence, can skip or reuse nonces.

**Impact**: Server can pre-compute favorable nonce values.

**Mitigation**:
- Nonce must be bound to transcript and visible
- Sequential enforcement with gap detection
- Public audit trail of all nonces used

### 1.9 Modulo Bias

**Description**: `entropy % N` introduces bias if entropy range isn't multiple of N.

**Technical Details**:
- With 256-bit uniform entropy, bias is tiny (~2^-248 for typical N)
- With truncated entropy (e.g., 32-bit), bias can be significant

**Impact**: Slight but measurable deviation from expected probabilities.

**Mitigation**:
- Use rejection sampling for strict fairness
- Document bias quantitatively if not eliminated
- Use sufficient entropy bits

### 1.10 Primedice Exploit (2014)

**Description**: $1M+ lost due to RNG system flaw allowing seed prediction.

**Lesson**: Even well-intentioned implementations can have subtle flaws.

## 2. Formal Threat Model

### 2.1 Threat Actors

| Actor | Capability | Motivation |
|-------|-----------|------------|
| Malicious Operator | Full server control, code modification | Increase house edge, steal funds |
| Compromised Employee | Partial server access | Financial gain |
| External Attacker | Network interception, client manipulation | Exploit vulnerabilities |
| Colluding Player | Multiple accounts, timing analysis | Beat the house unfairly |

### 2.2 Security Properties

**Property A: Post-Commit Immutability**
- Definition: Server cannot change committed seed after T1 without detection
- Guarantee: If commitment is binding and client verifies hash(reveal) = commit, then server cannot change seed after commitment
- Assumption: SHA-256 preimage resistance holds

**Property B: Unbiasability**
- Definition: Server cannot choose favorable outcomes
- Guarantee: Holds ONLY IF at least one input is unpredictable to server at commit time AND server cannot abort selectively
- Assumption: External randomness source or pre-committed seed chain

**Property C: Public Verifiability**
- Definition: Anyone can recompute outcome from transcript
- Guarantee: Given transcript and deterministic mapping, outcome is reproducible
- Assumption: Deterministic simulation across all environments

**Property D: Availability / Non-Selective Abort**
- Definition: Server cannot selectively void unfavorable outcomes
- Guarantee: All aborts are publicly logged and automatically refunded
- Assumption: Transparency log with append-only guarantees

## 3. Cryptographic Guarantees

### 3.1 What SHA-256 Commitment Provides

**Binding**: Server cannot change the seed after publishing its hash (assuming preimage resistance)

**Hiding**: Player cannot recover the seed from the hash (assuming second preimage resistance)

### 3.2 What SHA-256 Commitment Does NOT Provide

**Unbiasedness**: Commitment alone does NOT guarantee random seed selection. Server can grind seeds before committing.

**Timestamp Integrity**: Hash doesn't prove WHEN it was created.

**Parameter Binding**: Hash of seed doesn't bind other game parameters.

### 3.3 NIST Guidelines (SP 800-175B, SP 800-133)

- Use CSPRNG for all key/seed generation
- Minimum 256-bit security level for long-term secrets
- Key generation must be unpredictable and unbiased
- Document all cryptographic assumptions

## 4. Three-Body RNG Specific Analysis

### 4.1 Current Design Review

**Strengths**:
- Commit-reveal protocol with timeline (T1 < T2 < T3 < T4)
- 5 independent entropy sources (one per reel)
- Client seed contribution
- SHA-256 commitment

**Weaknesses**:
- Per-spin fresh server seeds allow grinding
- Browser timestamps don't prove server timing
- Three-body simulation determinism not guaranteed across environments
- No transparency log for commitments
- Verification code served by same operator

### 4.2 Critical Questions

1. **Is the three-body simulation bit-for-bit deterministic?**
   - Floating-point operations can vary across CPUs/browsers
   - If not deterministic, client cannot truly verify simulation

2. **What prevents server from grinding seeds?**
   - Current design: nothing explicit
   - Server can try many seeds, commit only to favorable ones

3. **How are timestamps verified?**
   - Current: browser-local only
   - No third-party attestation

4. **What parameters are committed?**
   - Current: only server seed hash
   - Missing: simulation parameters, mapping algorithm version, reel strips

## 5. Recommended Security Architecture

### 5.1 Seed Chain (Anti-Grinding)

```
Instead of: Generate fresh seed per spin
Use: Pre-committed seed chain

Day 0: Generate master_seed, publish hash(master_seed)
Spin N: seed_N = HMAC(master_seed, N)
        commitment_N = hash(seed_N)
        
Server cannot grind because master_seed is fixed before bets.
```

### 5.2 Transparency Log (Timing Proof)

```
┌─────────────────────────────────────────────────────────────┐
│                 TRANSPARENCY LOG                            │
├─────────────────────────────────────────────────────────────┤
│ Entry 1: { commitment, timestamp, signature, merkle_proof } │
│ Entry 2: { commitment, timestamp, signature, merkle_proof } │
│ ...                                                         │
│ Merkle Root → Periodic blockchain anchor                    │
└─────────────────────────────────────────────────────────────┘

Client requires inclusion proof BEFORE enabling "Spin" button.
```

### 5.3 Complete Commitment Structure

```javascript
commitment = SHA256(JSON.stringify({
  serverSeed: "...",
  gameVersion: "1.0.0",
  reelStrips: [...],
  mappingAlgorithm: "modulo-v1",
  simulationParams: {
    masses: [1, 1, 1],
    G: 1,
    dt: 0.001,
    steps: 10000
  },
  timestamp: "ISO-8601"
}))
```

### 5.4 Client Seed Best Practices

```javascript

const clientSeed = await generateSecureClientSeed();

// Allow user override

// Commit to client seed (optional, for two-party commit)

// Send clientCommitment to server BEFORE receiving server commitment

### 5.6 Abort Handling

```
IF reveal not received within 60 seconds:
  1. Log orphaned commitment to transparency log
  2. Automatic refund to player
  3. Increment operator abort counter (public)

## 7. Formal Security Proof Outline

### Theorem 1: Post-Commit Immutability

**Statement**: If SHA-256 is preimage resistant and client verifies hash(revealed_seed) = commitment, then server cannot change the committed seed after publishing commitment without detection.

**Proof Sketch**:
1. Assume server publishes commitment C = SHA256(S) at time T1
2. Server reveals S' at time T4
3. Client computes SHA256(S') and compares to C
4. If S' != S, then SHA256(S') != SHA256(S) = C (by collision resistance)
5. Therefore, verification fails if seed changed

### Theorem 2: Unbiasability (Conditional)

**Statement**: If (a) server seed is derived from pre-committed chain OR external beacon, (b) client seed is unpredictable to server at commit time, and (c) server cannot selectively abort, then server cannot bias outcomes.

**Proof Sketch**:
1. Pre-committed chain: server cannot change seed after chain published
2. Unpredictable client seed: server cannot compute outcome before client input
3. No selective abort: server must reveal all outcomes
4. Combined entropy from both seeds is unpredictable to either party
5. Therefore, outcomes are unbiased

### Theorem 3: Public Verifiability

**Statement**: Given complete transcript (commitment, client_seed, nonce, revealed_seed, parameters) and deterministic mapping algorithm, any party can independently compute and verify the outcome.

**Proof Sketch**:
1. All inputs are public after reveal
2. Mapping algorithm is deterministic and published
3. Anyone can execute: outcome = map(combine(server_seed, client_seed, nonce))
4. Compare computed outcome to claimed outcome
5. Verification succeeds iff outcomes match

## 8. Audit Trail System Design

### 8.1 Log Entry Structure

```typescript
interface AuditLogEntry {
  entryId: string;           // Unique identifier
  timestamp: string;         // ISO-8601
  entryType: 'COMMIT' | 'REVEAL' | 'ABORT' | 'REFUND';
  
  // Commitment data
  commitment?: string;       // SHA-256 hash
  gameId?: string;
  playerId?: string;         // Anonymized
  
  // Reveal data
  serverSeed?: string;
  clientSeed?: string;
  nonce?: number;
  outcome?: string;
  
  // Merkle proof
  merkleRoot: string;
  merkleProof: string[];
  
  // Signature
  signature: string;         // Operator signature
}
```

### 8.2 Merkle Tree Structure

```
                    Root
                   /    \
                  /      \
                H01      H23
               /  \     /  \
              H0  H1   H2  H3
              |   |    |   |
             E0  E1   E2  E3  (Log Entries)
```

### 8.3 Blockchain Anchoring

```
Every N entries OR every T minutes:
  1. Compute current Merkle root
  2. Submit transaction to blockchain:
     - Ethereum: Store root in smart contract
     - Bitcoin: OP_RETURN with root hash
  3. Record blockchain tx hash in log
```

## Appendix A: Glossary

| Term | Definition |
|------|------------|
| Binding | Property that prevents changing committed value |
| CSPRNG | Cryptographically Secure Pseudo-Random Number Generator |
| Grinding | Trying many seeds to find favorable outcome |
| Hiding | Property that prevents learning committed value |
| Merkle Tree | Hash tree for efficient verification |
| Preimage Resistance | Cannot find input given hash output |
| Seed Chain | Deterministic sequence of seeds from master |
| Transparency Log | Append-only public record |

|--------|-------------------------------|----------------------------|
